# HFL-DPIF-Reference-Implementation-for-Privacy-Preserving-EV-Charging-Scheduling

This repository provides a runnable reference implementation of a hierarchical federated learning pipeline for privacy-preserving electric vehicle charging scheduling. The code was prepared to address reproducibility concerns by offering an executable end-to-end example rather than a template or pseudocode fragment. The implementation loads the EV charging infrastructure dataset, constructs a station-level electric vehicle charging scenario, simulates Non-Independent and Identically Distributed data partitions across charging stations, trains a hierarchical federated prediction model with adaptive differential privacy, performs clustering-aware aggregation, refines scheduling decisions with an Alternating Direction Method of Multipliers style consensus step, and evaluates robustness under a Sharded Multicast with Stochastic Verification mechanism.

The main script is `hfl_dpif_reference_implementation.py`. It is designed as a single-file executable implementation so that the full experimental logic can be inspected, run, and modified without searching across multiple modules. The code reads the uploaded CSV dataset `ev_charging_stations_2010_2024.csv`, extracts station-level attributes such as location, charging type, station type, power output, gas station distance, electric vehicle adoption rate, popular vehicle models, and installation year, and then uses these station records to generate synthetic but structured electric vehicle charging sessions. This session generation stage creates the downstream learning problem and serves as a public reproducibility substitute when the original private operational charging traces are not part of the shared dataset.

The overall workflow begins with station-level data ingestion and synthetic charging-session construction. For each charging station, the code generates a configurable number of simulated vehicle sessions using station-dependent behavior distributions. The generation process creates realistic scheduling-related variables, including arrival hour, weekday indicator, initial state of charge, target state of charge, energy demand, dwell time, queue pressure, tariff level, renewable variability, and flexibility score. These variables are then used to define two targets. One target is a binary peak-demand label used for federated classification. The other is a continuous scheduling target used later in the ADMM-style scheduling refinement stage. The session generation logic intentionally produces heterogeneity across stations so that the federated training environment is meaningfully Non-IID.

The feature preprocessing pipeline handles both numerical and categorical variables. Numerical variables are normalized with standard scaling, while categorical variables are encoded using one-hot encoding. This preprocessing is implemented through a `ColumnTransformer` wrapped in a `Pipeline`, making the transformation reproducible and consistent between training and test sets. The processed feature matrix is then used to train a lightweight logistic model for peak-demand prediction. This choice keeps the reference implementation transparent and easy to run while still allowing the privacy, aggregation, and scheduling mechanisms to be demonstrated in a fully executable form.

The learning model itself is a logistic classifier implemented directly with NumPy rather than a deep learning framework. This was done to keep the public code simple, dependency-light, and auditable. The model contains a weight vector and a bias term. Local station updates are computed with gradient-based optimization, and each station trains from the same current global model. The local training loop includes differential privacy protection in the form of gradient clipping followed by adaptive Gaussian noise injection. The clipping threshold is controlled by `clip_norm`, and the noise scale is determined by the local privacy budget together with the adaptive noise parameters `dp_gamma` and `dp_tau`. This structure mirrors the manuscript logic that links privacy protection strength to gradient sensitivity and optimization stability.

The dynamic privacy budget allocation module implements the manuscript’s idea of balancing urgency and privacy sensitivity. For each station, the code estimates a privacy sensitivity score and a scheduling urgency score from local data statistics. These two quantities are then combined through the weights `omega_urg` and `omega_pri` to produce a station-specific privacy budget bounded between `epsilon_min` and `epsilon_max`. In practical terms, this means that stations with more urgent scheduling needs can be assigned a larger privacy budget and therefore less noise, while stations with more privacy-sensitive local information receive tighter privacy control. The implementation uses public, reproducible proxy variables to represent these quantities so the mechanism can run directly on the released dataset.

To address Non-IID data handling, the code includes a Mahalanobis-aware station clustering stage. Each station is summarized by a compact embedding computed from local averages such as charging power, adoption level, queue pressure, energy demand, dwell time, and local peak-demand rate. These embeddings are whitened using a covariance-based transform so that clustering reflects distributional relationships more meaningfully than raw Euclidean distance alone. KMeans clustering is then applied to group stations into a configurable number of clusters. This grouping creates the intermediate aggregation tier used by the hierarchical federated learning procedure. The default number of clusters is controlled by `num_clusters`, and this can be changed to support sensitivity analysis.

Hierarchical aggregation is implemented in two steps. Local station updates are first aggregated within each cluster using sample-size weighting, and the resulting cluster-level updates are then aggregated again at the global level. This design reflects a station-cluster-cloud hierarchy rather than a flat federated topology. The purpose of this structure is to reduce instability under Non-IID data, lower communication burden relative to flat broadcasting, and better match the layered operational organization of charging infrastructures. The implementation is intentionally explicit, so the user can inspect exactly how update vectors are computed and combined.

The scheduling refinement step is implemented with an Alternating Direction Method of Multipliers style consensus routine. Each station contributes its local scheduling target, and the algorithm iteratively updates local variables, a global consensus variable, and dual variables under a penalty parameter `rho`. The output includes a consensus schedule and a scheduling error percentage relative to local station targets. This stage is not intended to replicate a full optimal power flow solver. It instead provides a transparent public implementation of the manuscript’s distributed coordination logic in a way that is runnable and easy to extend. The ADMM parameter `rho` can be changed from the command line, which makes it suitable for sensitivity experiments.

The code also includes a Sharded Multicast with Stochastic Verification simulation to approximate the blockchain-style verification component described in the manuscript. This module allows the user to specify the number of nodes, malicious node ratio, number of verification shards, bandwidth, network delay, jitter, and node dropout rate. Based on these settings, the script estimates malicious-node detection rate, communication latency, retransmission overhead, and the number of verification shards used. A dynamic hardening mechanism is included so that when the simulated abnormal rejection rate exceeds a threshold, the number of verification shards is increased automatically. This makes the implementation useful for reproducing the qualitative behavior discussed in the robustness analysis under high Byzantine pressure.

For privacy evaluation, the code includes a membership inference attack routine. The attack compares the loss distribution of training samples and held-out samples under the trained global model and uses a threshold-based decision rule to estimate attack success. From this, the script computes a simple privacy protection rate summary. This is not a full industrial attack benchmark suite, though it is a runnable baseline that can be extended with stronger shadow-model or white-box attack implementations. The design goal here is to provide an executable privacy evaluation pipeline that users can inspect, improve, and report against.

The script is configured through command-line arguments so that experiments can be reproduced or modified without editing source code. The required argument is `--data-path`, which points to the CSV file. Optional arguments allow the user to set the output JSON path, random seed, maximum number of stations to use, number of simulated vehicles per station, number of clusters, global federated rounds, local epochs, learning rate, gradient clipping norm, privacy budget bounds, differential privacy parameters, dynamic budget weights, ADMM penalty parameter, ADMM iterations, and SMSV network settings. The default configuration uses a moderate workload so the script can run on a normal workstation without specialized hardware.

A typical run command is `python hfl_dpif_reference_implementation.py --data-path ev_charging_stations_2010_2024.csv --output-json hfl_dpif_results.json`. This command loads the charging-station dataset, generates the simulation environment, runs federated training and scheduling, evaluates privacy and verification behavior, and writes a structured JSON summary to disk. The JSON output includes the configuration, dataset statistics, round-by-round training history, final test metrics, ADMM scheduling summary, membership inference summary, SMSV verification summary, scheduling MAPE, privacy budget statistics, and cluster sizes. This makes it straightforward to archive results, compare runs, or feed outputs into a plotting script for figures and tables.

The main dependencies are Python 3, NumPy, pandas, and scikit-learn. No deep learning framework is required. This lightweight dependency set was chosen so that the code remains easy to install and run in public environments such as GitHub Codespaces, cloud notebooks, or standard university lab machines. A simple environment can be created by installing the required packages with pip. In practice, a minimal `requirements.txt` would include `numpy`, `pandas`, and `scikit-learn`. If the user later wants to add plotting utilities, `matplotlib` can be included as well.

This reference implementation should be understood as a public reproducibility baseline. It demonstrates the complete algorithmic pipeline in executable form, but it does not claim to be the exact internal source tree used in the manuscript experiments. Some components have been simplified so they can run directly on the released infrastructure dataset without access to private operational traces, proprietary scheduling engines, or deployment-specific blockchain services. Even with these simplifications, the code is structured to preserve the methodological logic of the framework and provide a solid basis for independent validation, ablation studies, extension experiments, and public repository release.

For a GitHub release, it is recommended to place the dataset in a `data/` directory, keep the main script in `src/`, store JSON outputs in `results/`, and include this README together with a `requirements.txt` file. It is also a good idea to add a short repository note explaining that the code is a fully runnable reference implementation prepared for reproducibility and that users may adapt the session generator, privacy module, or scheduling stage to match their own experimental assumptions more closely. This framing is honest, technically clear, and usually well received by reviewers because it gives them real executable code instead of a placeholder description.
